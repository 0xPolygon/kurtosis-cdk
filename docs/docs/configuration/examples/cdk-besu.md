# CDK Besu

These configurations run the L2 on a vanilla [Hyperledger Besu](https://github.com/hyperledger/besu) chain, with no CDK-specific or OP-specific execution client. Besu is connected to Agglayer exactly like any other sovereign chain: the bridge and global exit root contracts are predeployed in its genesis, the chain is registered on L1 as a sovereign rollup, and [AggKit](https://github.com/agglayer/aggkit) drives certificates and global exit root injection.

## Sovereign

The chain is a single-validator [QBFT](https://besu.hyperledger.org/private-networks/how-to/configure/consensus/qbft) network: one node is both the block proposer and the RPC endpoint. QBFT finalises every block as it is produced.

#### What gets deployed?

- L1 Ethereum blockchain (lighthouse/reth).
- Agglayer stack ([contracts](https://github.com/agglayer/agglayer-contracts), [agglayer service](https://github.com/agglayer/agglayer) and [mock prover](https://github.com/agglayer/provers)).
- L2 Besu blockchain (single QBFT validator) with the sovereign bridge and global exit root contracts predeployed in genesis, enhanced with [AggKit](https://github.com/agglayer/aggkit) for Agglayer connectivity.
- [zkEVM bridge](https://github.com/0xPolygonHermez/zkevm-bridge-service) to facilitate asset bridging between L1 and L2 chains.

#### Best For

- Validating that Agglayer's pessimistic proof path works against an unmodified, non-CDK execution client.
- Testing chain integrations that cannot adopt cdk-erigon or the OP stack.

#### Deployment

```bash
kurtosis run --enclave cdk --args-file .github/tests/besu/sovereign-ecdsa-multisig.yml .
```

#### Configuration

The QBFT validator is derived from `besu_validator_private_key`, and its address is encoded into the genesis `extraData` at deploy time, so the chain is reproducible from that key alone. Block cadence and gas limit are set with `besu_block_period_seconds`, `besu_epoch_length`, `besu_request_timeout_seconds` and `besu_gas_limit`.

:::info
`consensus_contract_type: ecdsa-multisig` and `qbft` (see [AggchainQBFT](#aggchainqbft) below) are supported, and the deployment fails early if anything else is selected. Besu produces no execution proof, so FEP does not apply. The older `pessimistic` consensus contract is excluded for a version reason: it has to be pinned to aggkit 0.5.4, and aggkit only began reading block hashes from the JSON-RPC response in 0.9 ([agglayer/aggkit#1397](https://github.com/agglayer/aggkit/pull/1397)). Before that it recomputed them with go-ethereum's RLP header hashing, which never matches a QBFT block hash because QBFT strips the committed seals from `extraData` first — so the L2 bridge syncer silently drops every block carrying events and no certificate is ever built. The aggsender still runs in `PessimisticProof` mode on `ecdsa-multisig`.
:::

:::warning
The chain runs with a zero base fee and accepts zero-priced transactions. Because QBFT has instant finality, Besu serves no `safe` or `finalized` block tags — components that follow the chain head are configured to track `latest`.
:::

## AggchainQBFT

With `consensus_contract_type: qbft` the rollup is an `AggchainQBFT` contract (`AGGCHAIN_TYPE` `0x0002`): instead of a multisig, every certificate carries an aggchain proof that the L2 headers in its range are sealed by a quorum of the QBFT validators and that the bridge state matches them. The proof is generated by `aggkit-prover-qbft` ([agglayer/prover-besu-qbft](https://github.com/agglayer/prover-besu-qbft)) and the aggsender runs in `AggchainProof` mode. `qbft` is accepted only with `sequencer_type: besu`.

#### What gets deployed?

On top of the sovereign Besu deployment above:

- `besu_validator_count` QBFT validators (`besu-001-validator-001` …) and a non-validator RPC node `besu-001` that aggkit, the bridge service and the prover talk to. The RPC node uses Forest storage (the prover reads `eth_getProof` at past blocks) and `besu_rpc_max_active_connections` HTTP connections.
- `AggchainQBFT` created on L1 and initialized from the running chain: the validators decoded from the genesis `extraData` (sorted), `besu_epoch_length`, the hash of block 0 and `l2_chain_id`, with no outstanding votes. The program vkey printed by `aggkit-prover-qbft vkey` is registered under selector `0x00010002` (override with `aggchain_qbft_vkey`).
- `aggkit-prover-qbft-001` (image `aggkit_prover_qbft_image`), started after the initialization; it checks `chainConfigHash()` against the chain before serving.

#### Deployment

```bash
kurtosis run --enclave cdk --args-file .github/tests/besu/sovereign-qbft.yml .
```

#### Configuration

- `besu_validator_count` (default `1`): with more than one, validator `n` uses the key at index `besu_validator_mnemonic_index_base + n - 1` (default base `100`) of `l1_preallocated_mnemonic`, and the RPC node the next index, so a validator vote can add it as a further validator. With `1`, the single node uses `besu_validator_private_key`, as above.
- `aggkit_prover_primary_prover` (default `mock-prover`), `aggkit_prover_qbft_max_headers_per_proof` (default `7200`) and `aggkit_prover_qbft_header_fetch_concurrency` (default `16`, must stay below `besu_rpc_max_active_connections`).

:::info
`aggkit-prover-qbft` has no published image yet, and `AggchainQBFT` support is on feature branches of agglayer-contracts, aggkit and agglayer: build those images and set `aggkit_prover_qbft_image`, `agglayer_contracts_image`, `aggkit_image` and `agglayer_image`. There is no mock aggchain program: with the mock prover the real program is executed and the real vkey is registered. `use_agg_sender_validator` is not supported, since `AggchainQBFT` is initialized without multisig signers.
:::
